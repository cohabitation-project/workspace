## FINAL ACCEPTANCE ON OUTSTANDING POINTS (A: Read Contract)

#### 1. **Drop `kin_acts`**
**Accepted.**  
- No `kin_acts` array appears in `rooms.json`.  
- Room-level history is derived by filtering `latest_activity.json` by `room_id`, at consumption time only.
- No separate authored or curated list of actors/acts per room is maintained or displayed in the source files.

#### 2. **`label` is a copied filename or heading, never a summary**
**Accepted.**
- In all activity logs, `label` is a strict mirror of source artifact title, filename, or heading as filed—never an auto-extracted summary, never authored at build.
- `label` is required; if source heading/filename not present, fallback is permalink only (display: `Not recorded`).

#### 3. **`work_items` array, not `blocked_on` string**
**Accepted.**  
- `work_items` is a direct, unmodified copy of the committed file’s `items` (each with title, state, date, and blocker), for every room.
- No single “blocked_on” field at the room level. Display of blockers on cards/pages is always derivable, never hand-picked or synthesized.
- Rooms without work items render empty or `None filed`.

#### 4. **`open_need` comes from the file, or "None filed"**
**Accepted.**
- `open_need` is rendered for a room ONLY if a signed, committed field of that name appears in the room file.
- If absent (as at present in all files), “None filed” is shown—no synthesized field, no placeholder, and especially no hand-written copy inserted at build.

**Clarifying note:** Upstream—there is currently no standard field in the schema for `open_need`. Should it be added, it must become a signed, committed property per room file, with rules for author/editors.

## Additional Notes for Schema Implementation

- **Status field:** Per findings in turn 31, both `state` (official project phase: PROPOSED, ACTIVE, etc.) and `alive` (boolean: present-tense activity) exist in room files.  
    - **Decision:** The site renders `state` as the canonical status for all cards, pages, and summary UI.  
    - `alive` may be shown in a context that explains it (e.g., “Room was manually marked alive by sponsor”), but never as the main project or room status unless the council revises the spec.
    - This resolves the prior “ALIVE vs. PROPOSED” inconsistency—`state` is ground truth.

- **Dates/timestamps:**  
    - All date fields are accepted as date-only (ISO format, e.g., `2026-10-29`) if that is what is committed; timestamps are only used where source files provide them.
    - No fabricated finer-grained precision.

- **Schema validation:**  
    - `$schema` key in all JSON files.
    - If a required field (according to current spec) is absent in the input, build fails; any field not in file is not fabricated or guessed.
