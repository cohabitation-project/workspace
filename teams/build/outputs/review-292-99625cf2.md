# Tier 1 review — PR #292, refunds, disputes and the split

**Verdict: NO on exact head `99625cf29e6a24fe5fce5696937ba7c4b28abe48` (short `99625cf2`).**

## Blocker — a valid paid-event replay reverses later money states

**File/line:** `commons/lib/checkout.mjs:198`, in `handleEvent`:

```js
if (cur.status !== 'paid') logOrder({ op: 'status', order: id, status: 'paid', ... });
```

This accepts `checkout.session.completed` / `async_payment_succeeded` from *every* non-`paid` state. It therefore overwrites the states this PR adds. Webhook signature verification proves origin, not freshness; a valid event can be delivered again or arrive after later events.

My exact-head review-only reproduction first established the passing boundaries above, then replayed the original paid-session object:

| Later state before replay | Expected after replay | Actual returned and folded state | Other retained evidence |
|---|---|---|---|
| fully `refunded` | `refunded` | **`paid`** | `refunded_cents: 2500` remains |
| `dispute_lost`, dispute status `lost` | `dispute_lost` | **`paid`** | the stored dispute still says `lost` |

The replay harness exited 1 on the intended assertion, after printing both actual transitions. Evidence: `teams/cut/outputs/2026-11-22T06-22-51/review292-replay.mjs` and `review292-replay.log`.

**Required fix:** make the paid-session transition state-aware/idempotent so it cannot overwrite partial/full refunds or dispute states. If a replay supplies a missing `payment_intent`, record that association without resetting the later money state. Add regression coverage for replayed/out-of-order paid events after at least a full refund and a lost dispute; include the partial-refund and open-dispute cases as well. Define the stale-event policy for dispute created/closed ordering too. A changed head requires a new exact-head review.
