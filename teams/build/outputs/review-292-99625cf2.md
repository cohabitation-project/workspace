## Blocker — a valid paid-event replay reverses later money states

**File/line:** `commons/lib/checkout.mjs:198`, in `handleEvent`:

```js
if (cur.status !== 'paid') logOrder({ op: 'status', order: id, status: 'paid', ... });
```

This accepts `checkout.session.completed` / `async_payment_succeeded` from *every* non-`paid` state. It therefore overwrites the states this PR adds. Webhook signature verification proves origin, not freshness; a valid event can be delivered again or arrive after later events.

My exact-head review-only reproduction first established the passing boundaries above, then replayed the original paid-session object:

| Later state before replay | Expected after replay | Actual returned and folded state | Other retained evidence |
|---|---|---|---|
| fully `refunded` | `refunded` | **`paid`** | `refunded_cents: 2500` remains |
| `dispute_lost`, dispute status `lost` | `dispute_lost` | **`paid`** | the stored dispute still says `lost` |

The replay harness exited 1 on the intended assertion, after printing both actual transitions. Evidence: `teams/cut/outputs/2026-11-22T06-22-51/review292-replay.mjs` and `review292-replay.log`.

**Required fix:** make the paid-session transition state-aware/idempotent so it cannot overwrite partial/full refunds or dispute states. If a replay supplies a missing `payment_intent`, record that association without resetting the later money state. Add regression coverage for replayed/out-of-order paid events after at least a full refund and a lost dispute; include the partial-refund and open-dispute cases as well. Define the stale-event policy for dispute created/closed ordering too. A changed head requires a new exact-head review.

## Blocking defect: a repeated paid event erases a refund state

`commons/lib/checkout.mjs:194–199` handles both `checkout.session.completed` and `checkout.session.async_payment_succeeded`. Line 198 writes `paid` whenever `cur.status !== 'paid'`, including when the order is already `partly_refunded`, `refunded`, `disputed`, or `dispute_lost`.

I measured this on the exact head with a review-only test appended to a copy of the branch's own `stripe-checkout.mjs` fixture:

1. Create and pay an order with payment intent `pi_review_replay`.
2. Send `charge.refunded` for 1000 of 2500 cents; the order becomes `partly_refunded`.
3. Deliver the **same paid session event again**, as an at-least-once webhook retry/replay must tolerate.
4. Expected `partly_refunded`; actual **`paid`** (`review-292-edge.mjs:177` in the temporary copy).

The focused harness ran the seven original tests plus three review tests: **9 passed, 1 failed**. The two other review tests passed: unknown refund **and dispute** both left the complete order fold byte-for-byte unchanged, and a zero-fee $25 split was `{ paid: 25, cohabi_fee: 0, seller_share: 25, refunded: 0 }` with fee + seller share = paid. Evidence: `teams/build/outputs/2026-11-22T06-23-54/review-292-full-runtime.log`.

The essential added regression was:

```js
const paid = { type: 'checkout.session.completed', data: { object: {
  id: 'cs_review_replay', payment_status: 'paid',
  payment_intent: 'pi_review_replay', metadata: { cohabi_order: r.order }
} } };
checkout.handleEvent(paid);
checkout.handleEvent({ type: 'charge.refunded', data: { object: {
  id: 'ch_review_replay', payment_intent: 'pi_review_replay',
  amount: 2500, amount_refunded: 1000
} } });
assert.equal(checkout.order(r.order).status, 'partly_refunded');
checkout.handleEvent(paid);
assert.equal(checkout.order(r.order).status, 'partly_refunded'); // actual: paid
```

This is post-signature event-fold logic: the direct `handleEvent` probe intentionally isolates what happens **after** the webhook has been authenticated. It is not a claim that an unsigned stranger can call `handleEvent` through HTTP.

**Required fix:** make the paid-session transition idempotent and state-aware. Normally it should advance only `awaiting_payment` and no-op an already `paid` order; it must not regress later refund/dispute (or fulfillment) states. If older orders need a payment-intent backfill, separate that from the status transition. Add regression coverage for a repeated paid event after at least partial and full refunds; consider the dispute states as well. A changed head needs a fresh review.

- **Wallet wording:** `feedv2.mjs:688–693` has distinct words for partly refunded, refunded, disputed and dispute lost. The Sales row shows cut/share/refunded only on the seller's row.
