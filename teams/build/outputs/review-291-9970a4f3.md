## The five checks you asked for
1. **Art must be the maker's own upload: holds.**
   - `printful.mjs` `startMockup`: `images.get(art)` must exist, and `it.by === member.id || it.for === member.id`, else 403.
   - The test covers it: another member's image gets 403, and signed-out gets 401.
   - Caveat: "own upload" means "uploaded into our library by you". `images.fetchLink` lets a member import any https picture, and nothing here checks rights. The listing form's `rights: true` is self-attested. That matches the existing market, so it is not new, but it is worth a sentence in the terms before orders open.
2. **Token only in the Authorization header: holds.**
   - `PRINTFUL_TOKEN` appears in `printful.mjs:34`, as `authorization: Bearer …`, and in `fulfillment.mjs:90` (`send`), also as a header.
   - It is never in a URL, a response body or a log line. The test asserts `seen.auth.every(a => a === 'Bearer test-token')`.
   - Error text echoes at most 160 characters of Printful's `error.message`. Printful is trusted not to echo the token. I did not verify that against the real API.
3. **Price can't go below base cost: holds, with a limit.**
   - `/api/merch/listings`: `if (!(amount >= t.base))` returns 400. NaN or a missing amount is refused too, because the comparison is false.
   - The test covers $10 against a $12.95 base.
   - The limit is that the floor is the base price of the variant at mockup time, and it excludes shipping. See defect #4.
4. **A mockup publishes once: holds.**
   - `takeTask` then `forgetTask` run in the same synchronous handler, so two concurrent publishes can't both pass.
   - If `fulfillment.link` throws, the listing is withdrawn and the task is kept, so the maker can retry. This is sensible.
   - The test asserts the second publish returns 404.
   - Tasks live in memory, so a server restart loses an unpublished mockup. Harmless, but the maker must redo it.
5. **No order reaches Printful: holds.**
   - `fulfillment.send` is the only place that POSTs `/orders`, and it refuses unless `paymentsOpen()`, the order is `paid`, and the pipe is connected.
   - `printful.mjs` only calls `/products`, `/mockup-generator/printfiles`, `/mockup-generator/create-task` and `/mockup-generator/task`.
   - The test never touches `/orders`.

## Defects

### 1. An empty or failed product list is cached for 6 hours (medium, fix before production)
- **File and line:** `commons/lib/printful.mjs`, `products()`. It catches each product's error, rethrowing only status 503, and then does `cache = out; cacheAt = Date.now()` even when `out` is empty.
- **Reproduced (measured):** with every Printful call answering 429, `products()` returns `[]` after 8 calls (4 curated products × 2 calls). A second call a moment later makes **0 further calls** and returns the cached `[]`.
- **Consequence:** one Printful hiccup, 429 or timeout, on the first request after a deploy leaves `/api/merch/products` empty for 6 hours. The panel in `market.js` hides itself when `products.length` is 0, so no maker sees "Make it a product". There is no error message.
- **Fix:** don't cache an empty list, or cache it for about 60 seconds. Better, keep the last good list and refresh it on failure. Add a test that fails every call, then succeeds, and expects products on the second call.
- **Related:** `GET /api/merch/products` is unauthenticated. An uncached failure repeats the 8 calls per request. A short negative cache fixes this too.

### 2. `plan()` ignores the stored `design`, and the order shape looks wrong (medium, before orders open; inferred)
- **File and line:** `commons/lib/fulfillment.mjs`, `plan()`, the printful branch. It sends `items: [{ sync_variant_id: Number(lk.variant_ids[0]), quantity }]`.
- **Gap:** #291 stores `design` (art id, placement, position) and the catalog `variant_id` from the mockup flow. The order body uses neither `files` nor a catalog `variant_id`.
- **Inferred, not tested:** from my memory of Printful's API, `sync_variant_id` means a variant of a sync product already in the store. The mockup flow never creates one, so an order for these listings would probably be refused. Printful's `/orders` accepts catalog `variant_id` plus `files: [{ url, … }]`. Check this against Printful's current docs before building on it.
- **Why it isn't a blocker:** orders are closed, and the PR says so. But the comment "needed to print it later" in `link()` promises something `plan()` doesn't do yet. The next job needs a test that the order body for a merch listing carries the art's public URL and position.

### 3. `design.art` is not checked on the generic link route (low now, medium once #2 is fixed)
- **File and line:** `commons/lib/fulfillment.mjs`, `link()`, line about 90. `design.art` is stored as `String(design.art).slice(0,40)` with no ownership check.
- **Route:** `POST /api/market/listings/:id/fulfillment` (`server.mjs`) passes the request body straight to `link()`. A maker can link their own listing with `design: { art: <someone else's image id> }`, which skips the "your own art" rule that `startMockup` enforces.
- **Not reproduced:** I read this and did not run it.
- **Consequence:** none today, because `plan()` ignores `design`. Once `plan()` prints from `design.art`, this is a way to print another member's art under your name.
- **Fix:** in `link()`, drop `design` unless `images.get(design.art)` is owned by the member, or accept `design` only from the printful.mjs path.

### 4. The price floor leaves out shipping, and the panel's copy goes further than the code (low; copy and honesty)
- The panel says: "Printful's base cost: $X. Set your price above it; the difference is yours. Shipping is added at checkout."
- Nothing in this PR adds shipping at checkout, and the Stripe/fee layer isn't part of it. "The difference is yours" is true only while our cut is 0%, which NOW.md says holds until decided.
- Once payments open, a price equal to base cost loses money on shipping and processing fees. Soften the copy to "the difference is before fees and shipping, which are set when payments open", or remove the unverified claim.

## Smaller notes (no action needed for the yes)
- The mockup rate limit (default 2 a minute) is shared Commons-wide. One maker can lock the others out for a minute. That is honest and the message says so. A per-member cap would fix it, but it is not needed now.
- `mockupResult` is not guarded against two polls arriving before `t.image` is set. Both fetch and upload. `images.upload` appears to dedupe identical bytes, but I didn't check that.
- Currency: `base_from` and the 400 message assume dollars (`$`), while the product carries `currency`. Fine for the US-only test phase.
